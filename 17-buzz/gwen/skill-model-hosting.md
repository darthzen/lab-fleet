---
name: model-hosting
description: Download a GGUF model, run it on llama-server on the two V100s as a test pod, measure it, and tear it down.
---
Hosting a local model on sdf1 has four parts: the image, the model file, a test pod, and the teardown. Load the kubernetes skill too. Starting anything on the GPUs needs Rick's say-so in the conversation, and llama-server, Ollama and ComfyUI in namespace ai must be at 0 replicas first: check with `kubectl -n ai get deploy llama-server ollama comfyui`.

The image. Production llama-server uses the upstream image named in ~/src/lab-fleet/26-llama-server/llama-server.yaml. When a model needs a newer llama.cpp than upstream publishes as an image, check which release added the architecture (the pull request on github.com/ggml-org/llama.cpp and the release tag after it), then use or build `registry.ash4d.com/ash4d-lab/llama-server-cuda:<release>-<n>`. The Containerfile is in ~/src/llama-server-cuda on your machine: BCI base, the release's ubuntu-cuda-12.8 tarball plus its cudart tarball. b12611-1 exists and runs on the V100s.

The model file. Models live on the node at /var/lib/models/<model>/<source>-<quant>/, mounted into pods as a hostPath at /models. Download with a Job in namespace ai, not on your machine (your disk is small). Read the expected size and sha256 first: `curl -s https://huggingface.co/api/models/<repo>/tree/main/<dir>` gives `size` and `lfs.oid` per file. Hugging Face throttles one long connection to about 2 MiB/s after a few GB; split the file into 8 byte ranges with `curl -r start-end` in parallel, `cat` the parts in order, then check the size and run `sha256sum -c`. A file is done only when the sha256 matches. Never let two downloaders write the same file: wait for the old pod to be gone before starting another.

The test pod. A plain Pod in namespace ai, applied with kubectl from ~/deploy/<name>/pod.yaml, never through lab-fleet. Copy from 26-llama-server/llama-server.yaml: `runtimeClassName: nvidia`, the nvidia.com/gpu toleration, the `NVIDIA_VISIBLE_DEVICES` UUID pair, `NVIDIA_DRIVER_CAPABILITIES`, `CUDA_CACHE_PATH=/nv-cache` with the /var/lib/models/.nv-cache hostPath, the /var/lib/models hostPath read-only, and `imagePullSecrets: harbor-pull` for a Harbor image. No nvidia.com/gpu resource request. Start from the production arguments and change only what the model forces.

Measuring. Follow `kubectl -n ai logs` until "listening" or a failure; the first start compiles CUDA kernels and can take minutes. Report the exact error lines on failure. When it is up: `nvidia-smi` through `kubectl exec` for memory per GPU, then chat completions against the pod IP with the request body in a file (`curl -d @body.json`), because JSON inside a shell command inside a tool call breaks on quoting. Read prompt and decode tokens per second from the `timings` block. Test one short prompt and one long one; a reasoning model can spend a small max_tokens entirely on reasoning and return empty content.

Teardown. Delete the pod, confirm `kubectl -n ai get pod <name>` says NotFound. The job is not done while a test pod holds a GPU.

Known for Inkling 2 Mini (architecture inkling2_loop, llama.cpp b12611, 2026-11-23): use the files under Mainline_Support/ in unsloth/Inkling-2-Mini-GGUF, renamed from .gguf_file to .gguf. `--split-mode tensor` is not implemented for this architecture; `--split-mode layer` loads but fills GPU0 (32 GiB at 32k context with the Q8_K_XL file) and leaves GPU1 mostly empty, and the mmproj then fails to allocate. About 17 tokens per second decode. Making it production-ready means solving that memory layout first: a smaller quant, a smaller context, or an uneven `--tensor-split` in layer mode.
